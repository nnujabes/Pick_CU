# finetune_v1 — 문장 → 조건 JSON 변환 (파인튜닝 1차)

> **1차 잠정 모델이며 test는 2026-11-06에 1회 측정했습니다(아래 "최종 test 측정 결과").**

## 목적

사용자 문장을 DB 조회용 조건 JSON으로 바꾸는 `parse_query()`와, 이를 위해 파인튜닝한 LoRA 어댑터를 공유합니다.
팀원 각자의 PC에서 파인튜닝 모델을 돌려볼 수 있게 하는 것이 목적이고, 학습 코드와 결과는 기록용으로 함께 둡니다.

## 폴더 구조

```
finetune_v1/
├─ code/
│  ├─ query_parser.py        ← 팀원이 쓰는 함수 (parse_query)
│  ├─ check_query_parser.py  ← 확인 테스트 (기록용)
│  └─ train_qlora.py, prepare_data.py, bench_train.py, dev_pair_baseline.py  ← 실험 기록용
├─ adapter/best/             ← LoRA 어댑터 (adapter_model.safetensors는 git에 없음, 따로 공유)
├─ results/                  ← 학습·평가·확인 테스트 결과
├─ test_results/             ← 최종 test 1회 측정 기록 (2026-11-06, test_data/는 학습·튜닝 금지)
├─ baseline_results/         ← 파인튜닝 전 기준 성능
├─ data_info/                ← 데이터 분할·수정 내역 (데이터 자체는 ../dev_pair_v3_baseline/에 있음)
├─ requirements.txt, env_info.txt  ← 서버에서 확인한 패키지 버전·환경
└─ MANIFEST.txt, SHA256SUMS.txt    ← 묶음 파일 목록·해시 (서버 원본 기준)
```

|---|---|

| best | epoch 1 (4 epoch에서 조기 종료) |
| 시스템 프롬프트 sha256 | 학습 때 `06818f0f…b556`, 2026-11-06부터 실제 사용 `836df788…80d7` (= 학습 프롬프트 + 관계없는 문장 규칙, 불러올 때 둘 다 자동 확인) |

## 사용법

```python
import sys
sys.path.insert(0, "members/hayoung/finetune_v1/code")
from query_parser import parse_query

parse_query("5천원 이하로 운동 후에 먹을 거")
# {"budget": 5000, "nutrients": {"단백질": "high", "지방": "low"}}
parse_query("야식으로 먹을 건데 2만원대로 짜지 않은 거")
# {"budget": 20000, "nutrients": {"나트륨": "low", "지방": "low"}}
parse_query("요즘 혈당이 걱정돼요")
# {"budget": null, "nutrients": {"당류": "low", "열량": "low"}}   ← 파이썬에서는 None
```

(위 결과는 서버 GPU에서 3번 반복해 같게 나온 값입니다.)

- 반환 형식: `{"budget": 정수 또는 null, "nutrients": {"단백질": "high", "지방": "low"}}`
  - 성분 이름: 열량·단백질·나트륨·탄수화물·당류·지방, 방향: `high`/`low`, 항상 2개
  - 예산은 모델이 아니라 규칙 코드(`extract_budget`)가 뽑습니다. 예산은 **상한**으로만 쓰므로, 상한이 아닌 금액("만원 넘게", "2천원 빼고" 등)은 `null`이 됩니다.
- **실패하면 `None`** (빈 입력, 300자 초과, 조건 없는 입력, 모델이 관계없는 문장으로 판단, 모델 응답 형식 오류, 실행 오류). 이유는 `logging` 경고로 남습니다.

### 조건 없는 입력·관계없는 문장 (2026-11-06 추가)

두 단계로 거릅니다. 둘 다 `parse_query`는 `None`을 돌려줍니다.

**1단계: 규칙 사전 검사 (모델 호출 없음)**

- 동작: "안녕하세요", "고마워", "ㅋㅋ", "추천해줘", "먹을 거 추천해줘"처럼 **인삿말·잡담·일반 요청어만 있는 입력은 모델을 부르지 않고 `None`**을 돌려줍니다(`is_no_condition`). 모델은 어떤 문장이든 영양소 2개를 고르도록 학습되어, 이 검사가 없으면 인사에도 영양소를 지어냈습니다.
- 규칙: 공백·문장부호·이모지와 ㅋ·ㅎ·ㅠ 같은 웃음·울음 표시를 지운 뒤, 코드 위쪽 목록(`_CHITCHAT_WORDS`, `_REQUEST_WORDS`, `_FILLER_WORDS`)의 말을 모두 지워 **남는 글자가 없을 때만** 거릅니다. 길이로는 거르지 않습니다. "안녕하세요 단백질 높은 거", "야식 추천해줘"처럼 다른 말이 남으면 모델로 보냅니다.
- 단어 목록 기반이라 목록에 없는 잡담("오늘 날씨 어때" 등)은 2단계로 넘어갑니다. train v3·dev v3 3,036문장 중 이 검사에 걸리는 문장은 0개입니다.

**2단계: 프롬프트의 관계없는 문장 규칙 (팀원 실험 반영)**
- 학습 프롬프트 끝에 `UNRELATED_RULE`을 덧붙였습니다: 먹을 것·식사·건강·몸 상태·상황과 관계없는 문장(인사, 잡담, 날씨, 감사 인사, 다른 주제 질문 등)이면 영양소를 고르지 말고 `{"nutrients": []}`로만 답하라는 규칙입니다.
- 모델이 빈 목록으로 답하면 `parse_query`는 `None`을 돌려주고 로그에 "관계없는 문장(모델이 빈 목록으로 답함)"을 남깁니다(형식 오류 로그와 구분).
- **어댑터는 이 규칙 없이 학습했습니다.** 실제로 쓰는 프롬프트가 학습 때와 다르므로, 아래 수치는 이 프롬프트로 다시 잰 값입니다.
- 확인 결과 (WSL RTX 4060, 4bit, 2026-11-06):
  - dev v3 216문장 완전 정답 **185/216 = 85.6%** (규칙 넣기 전 186/216 = 86.1%). 정상 문장이 `None`이 된 것 1개: "1,500원에 우는 아이 그치게 할 만한 게 뭘까요?"(관계없음으로 판단), 형식 오류 0.
  - 규칙 목록에 없는 잡담 8개("오늘 날씨 어때", "너 이름이 뭐야", "심심해", "뭐해 지금", "내일 서울에서 부산 가는 기차 시간 알려줘", "친구한테 3만원 빌렸는데 언제 갚지" 등) 모두 `None`, 문장당 약 0.7초.
  - 팀원 측정(같은 모델·어댑터): test 240문장 206 → 207개, 정상 문장 3개가 `None`. 이 결과를 보고 프롬프트를 정했으므로 test 수치는 참고용입니다(85.8%는 규칙 넣기 전 최종 성적).
- 한계: 영양소 단어가 없는 정상 요청("우는 아이 그치게 할 만한 거", "파티 간식" 등)이 가끔 관계없는 문장으로 걸러질 수 있습니다. "배고파", "점심 뭐 먹지"는 먹을 것과 관련된 말이라 영양소가 나옵니다.

**화면 안내**: `classify_failure(text)`가 모델을 부르기 전에 걸러진 이유를 돌려줍니다(`parse_query` 반환 형식은 그대로). 2단계에서 걸러진 경우는 모델을 불러야 알 수 있어 `None`이 나옵니다.

| `classify_failure` 반환값 | 뜻 | 권장 안내 문구 |
| --- | --- | --- |
| `"empty"` | 빈 입력·공백 | 원하는 조건을 입력해 주세요. |
| `"too_long"` | 300자 초과 | 문장을 짧게 줄여서 입력해 주세요. |
| `"no_condition"` | 인삿말·잡담만 있음 | 원하는 음식이나 영양 조건을 알려주세요. 예: '단백질 높고 지방 낮은 걸로 찾아줘' |
| `None` 인데 `parse_query`가 `None` | 모델이 관계없는 문장으로 판단, 또는 응답 형식 오류·실행 오류 | 영양 조건을 이해하지 못했어요. 예: '단백질 높고 지방 낮은 걸로 찾아줘' |

### `None`의 이유 받기: `parse_query_with_reason` (2026-11-06 추가, 혁준 요청)

`parse_query`는 실패 이유를 로그에만 남기므로, 이유가 필요한 쪽(종호 API)은 `parse_query_with_reason(text)`를 씁니다.
**`parse_query`의 동작과 반환값은 그대로**이며, 내부에서 `parse_query_with_reason(text)[0]`을 돌려줍니다.

```python
from query_parser import parse_query_with_reason
parse_query_with_reason("5천원 이하로 운동 후에 먹을 거")  # ({"budget": 5000, "nutrients": {...}}, None)
parse_query_with_reason("안녕하세요")                      # (None, "no_condition")  모델 호출 없음
parse_query_with_reason("오늘 날씨 어때")                  # (None, "unrelated")
```

이유 코드(팀 공통, 혁준 화면·종호 API가 글자 그대로 씀):

| 코드 | 뜻 | 정하는 곳 |
| --- | --- | --- |
| `empty` | 빈 입력 | 모델 호출 전 (`classify_failure`) |
| `too_long` | 300자 초과 | 모델 호출 전 (`classify_failure`) |
| `no_condition` | 인삿말·잡담·일반 요청어만 있음 | 모델 호출 전 (`classify_failure`) |
| `unrelated` | 모델이 관계없는 문장으로 판단 (`{"nutrients": []}`) | 모델 응답 |
| `invalid_output` | 모델 출력 형식 오류 (JSON 없음, 2개가 아님, 허용되지 않은 성분 등) | 모델 응답 |
| `error` | 실행 중 예외 (GPU 메모리 부족 등) | 예외 처리 |

성공하면 이유는 `None`입니다. 검사 순서(빈 입력 → 300자 → 인삿말 → 모델)와 로그 문구는 이전 `parse_query`와 같습니다.

- 어댑터 경로: 기본은 `finetune_v1/adapter/best`. 다른 곳에 두었으면 환경변수로 바꿉니다.
  ```
  set QUERY_PARSER_ADAPTER=D:\models\adapter_best      (Windows cmd)
  export QUERY_PARSER_ADAPTER=/path/to/adapter_best    (Linux/macOS)
  ```
- CLI: `code` 폴더에서 `python -m query_parser "5천원 이하로 운동 후에 먹을 거"`
- 첫 호출 때 모델을 한 번 불러 캐시하고, 이후 호출은 문장당 약 0.8초(RTX 4090 기준)입니다.

  1. torch는 PC의 CUDA 버전에 맞게 먼저 따로 설치 (https://pytorch.org 의 안내 명령 사용)

## 기록용 코드 안내

`train_qlora.py` 등은 서버 경로 기준의 실험 기록용이며 그대로는 재현되지 않을 수 있습니다.
`results/`의 json에 남은 서버 경로(`/home/dgu/...`)도 기록 그대로 두었습니다(저장소가 비공개라 바꾸지 않음).
저장소 복사본에서 바꾼 것은 `code/query_parser.py`의 `DEFAULT_ADAPTER` 한 줄(`ckpt/run_r16_lr2e-4/best` → `adapter/best`)과,
2026-11-06에 반영한 예산 추출(`extract_budget`, 종호 수정안 PR #22) 부분, 그리고 `code/check_query_parser.py`의 예산 단위 테스트(`BUDGET_CASES`: 기대값 4개 변경, 17개 추가)입니다.
같은 날 조건 없는 입력 검사(`is_no_condition`, `classify_failure`, `parse_query`의 사전 검사 3줄)와 그 테스트(`NO_CONDITION_CASES` 35개, `CONDITION_CASES` 7개, 호출 흐름 3개)도 추가했습니다. 확인 결과: 조건 없는 입력 44/44, 호출 흐름 9/9, 예산 77/77, 응답 변환 13/13.
같은 날 팀원 실험대로 시스템 프롬프트에 관계없는 문장 규칙(`UNRELATED_RULE`)을 덧붙이고 `SYSTEM_PROMPT_SHA256`을 바꿨습니다. 학습 프롬프트는 `TRAIN_SYSTEM_PROMPT`로 그대로 남겨 두고 ft_data와 같은지 확인합니다. 빈 목록 응답 검사 1개를 추가해 응답 변환은 14/14입니다.
같은 날 `parse_query_with_reason`을 추가하고 `parse_query`는 이를 감싸게 바꿨습니다(동작·반환값 동일). 이유 코드 검사 7개를 추가했습니다.
그래서 `SHA256SUMS.txt`의 `query_parser.py`, `check_query_parser.py` 해시는 서버 원본 기준이라 이 복사본과 다릅니다.
`results/query_parser_check_v2/offline.json`은 수정 전 예산 함수로 만든 기록이라 그대로 두었습니다. 수정 후 확인 결과: 예산 단위 테스트 77/77, 응답 변환 13/13, 호출 흐름 4/4, train v3·dev v3의 예산 포함 774문장 모두 추출·다른 유형 2,262문장 오탐 0. (이 문단은 예산 수정 시점 기준이며, 이후 프롬프트 규칙 추가로 dev는 85.6%가 되었습니다. 위 "조건 없는 입력·관계없는 문장" 참고.)
